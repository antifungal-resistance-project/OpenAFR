## Problem Statement
OpenAFR has three technically deep tracks (a CYP51 triage tool, a genotype→verdict
diagnostics engine, a genomic surveillance watch) but no named user for any of them,
and this is explicitly a side project, not a company. The surveillance track is the
only one that can produce a *shareable, self-running object* with zero customer setup
and no data the project doesn't already have. The goal here is not a product — it's a
thing worth showing a friend that keeps the project fun to poke at.

## What Makes This Cool
A single public URL — a "resistance weather report" — that quietly watches NCBI for new
*C. auris* genomes, runs the ERG11 re-caller + structural verdict when one lands, and
shows the result: a status line ("last new azole-resistance variant seen: N days ago"),
a running log, and a side-by-side render of the mutated CYP51 pocket vs wild-type so you
can *see why the verdict flipped*. Nobody expects a surveillance feed to show them the
chemistry. It runs itself while you sleep. Even a quiet feed reads well ("40 days quiet,
last hit was X") — the object is alive either way.

## Constraints
- Side project / for fun. No revenue goal, no users to satisfy, no regulatory path.
- Solo builder. Must be self-running and free to host — no server to babysit.
- Reuse the 80% already built: `openafr/alert.py` (surveillance ↔ structural coupling) is
  the single entrypoint the daily job calls; it fans out to `openafr/structural.py`,
  `openafr/mapping.py`, and the ERG11 re-caller.
- Novel / unknown ERG11 variants have no continuous score by design; the verdict for those
  is a mechanism-based structural best-guess label, not silence (matches the existing
  novel-variant handling). The page should show that label, not a blank.
- The ERG11 re-caller has a known compute/disk ceiling in the lean Docker image; heavy
  re-calling needs a cloud Linux VM (see recaller-run-environment memory). The page's
  daily job must stay within what a GitHub Action runner can do, or offload the heavy
  step. This is the main feasibility question (see Open Questions).

## Premises
1. New *C. auris* genomes land in NCBI often enough that the feed isn't permanently dead.
   — **CONFIRMED (2026-09-17 NCBI probe):** 1,093 total assemblies; 539 released in the last
   12 months (~45/mo); 179 in the last 3 months (~2/day). The feed is lively. A resistance
   hit is a subset of these but will still recur regularly, not annually.
2. The existing structural core can render a wild-type-vs-mutant pocket image
   non-interactively (headless), suitable for a static PNG. — Assumed from `structural.py`;
   confirm it can emit an image without a GUI.
3. The daily watch + re-call + render fits inside a free scheduled runner, OR the heavy
   re-call can be pre-computed / offloaded so the page build stays light. — Open.

## Approaches Considered
### Approach A: Static feed on a schedule (CHOSEN — with a compute-placement fork)
A daily job runs: NCBI watch → `alert.py` (re-caller / structural verdict) → writes an
`events.json` + a pre-rendered pocket PNG per hit → regenerates `index.html` → GitHub Pages
serves it. Free, no infra, reuses the existing modules almost as-is.

**The one fork to resolve before building** (see Open Question "compute placement"): the
ERG11 re-caller's known disk/compute ceiling may not fit a free Action runner. If it
doesn't, the real Approach A is the *split* design — the heavy re-call runs on the cloud
Linux VM and writes a small result artifact; the GitHub Action only fetches that artifact
and does the light render + Pages deploy. Treat the Action-only version as the optimistic
case and the split as the fallback; Next Step 1/3 decides which. "CHOSEN" is the shape, not
a claim that Action-only will fit.

### Approach B: Small dynamic app (rejected for now)
Next.js on Vercel with an in-browser 3D pocket viewer (3Dmol.js/NGL). Rejected: an
always-on server and deploy pipeline to maintain for a fun project; the 3D viewer bolts
onto A later if the itch appears.

### Approach C: The poster that draws itself (deferred)
Same cron backbone as A, but the page is generative art — one striking screen, the newest
pocket animates in, built to be screenshotted. Deferred: highest delight, but skimps on
the monitoring side; graft the animation onto A once A is live.

## Recommended Approach
Approach A, refined by the eng review against the actual code:

**The page is a thin view over `delivery.py`, not a new pipeline (eng-review Issue 1 → 1A).**
`delivery.py` already runs on a schedule, is stateless between runs with "the repo as the
only store" and "git history as the delivery log" (delivery.py:41-43), decides what's new,
stays silent on quiet runs (`is_noop`), and commits a digest. `alert.py` already renders
every event as Markdown AND JSON with ACT-NOW/WATCH/CONTEXT priority. So the daily job,
state, dedup, and write-back are ALREADY BUILT. New work = an HTML view over the JSON
`delivery.py` already produces + a GitHub Pages publish step. Do NOT build a parallel
`events.json` pipeline; adapt at the view layer if the page needs a different shape.

**The pocket image is pre-rendered out-of-band and committed as an asset (eng-review Issue 2
→ 2A).** The wild-type-vs-mutant pocket render is NOT in the offline path — `structural.py:247`:
"PyMOL is out of the offline verdict path." What `structural.py` emits is a `render_hint`
string (`mutate_receptor.py` → `make_pose_view.py` → `render_views.sh`), which needs PyMOL +
the pinned env and will NOT run in a free GitHub Action. So: when a new buildable variant
appears, run the existing `render_views.sh` chain once out-of-band (locally or on the cloud
VM), commit the PNG as a repo asset (e.g. `docs/pockets/<token>.png`), and the page/Action
just reference it. PyMOL never touches the Action. This is the same "repo is the store"
model as 1A.

## Open Questions
- **Deposit frequency** (Premise 1): how often do new *C. auris* genomes actually appear
  in NCBI? Decides update cadence and whether the "weather" metaphor holds.
- **Compute placement** (Premise 3): can the daily re-call run inside a GitHub Action, or
  does the heavy step need to be offloaded to the cloud VM with the page build only
  consuming a pre-computed result? Resolve before committing to the Action-only design.
- **Headless render** (Premise 2): confirm `structural.py` can emit a pocket PNG without a
  display.

## Success Criteria
- A public URL exists that a stranger can open and immediately understand.
- It updates itself on a schedule with no manual step.
- When a resistance-conferring ERG11 variant appears, the page shows the mutated pocket
  next to wild-type with a verdict.
- You'd send the link to a friend unprompted.

## Distribution Plan
GitHub Pages serving a static site, rebuilt and redeployed by a scheduled GitHub Action
(daily cron). No package, no binary — the deliverable *is* the URL. Optional later: an RSS
feed / bot (the deferred "make it emit" unlock) so the page pings instead of being polled.

## Data Contract (view layer, 1A) — verified against code 2026-09-17
The page reads `alert.render_json(compose_alerts(records, as_of))` (alert.py:341,149) → dict:
```
{ as_of, window_days, thresholds, coverage, note?,
  alerts: [ {
    mutation, canonical,
    emergence: { first_appearance, rising, possible_backlog, backlog_reason,
                 recent_count, recent_called, ... },
    regions, first_seen,
    priority: "ACT-NOW" | "WATCH" | "CONTEXT",
    headline,
    structural: { evidence_class, confidence, direction, fluconazole_fit_verdict,
                  lost_contacts, empirical, caveats },
  } ] }
```
Page mapping: `structural.direction` / `fluconazole_fit_verdict` → the "verdict flipped"
line; `priority` → row color; `first_seen` / `regions` / `emergence.recent_count` → status
line; `mutation`/token → `docs/pockets/<token>.png`. Committed delivery target already exists
at `data/earlywarning/digest/` with `STATE.json`.

## Sequencing Dependency (flagged by eng review)
`data/earlywarning/digest/STATE.json` = `{"delivered":{},"updated":""}` — the delivery
pipeline has NEVER had a real run. Real hits are downstream of running the ERG11 re-caller +
`delivery.py` on real data, which is itself gated on the cloud Linux VM (the known re-caller
run-environment blocker). Build order: the page can ship TODAY showing the day-0
"watching since…" state; it shows real resistance hits only after that VM run happens. The
page is not blocked — its content is.
